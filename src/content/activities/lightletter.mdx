## 담당 역할

CNN 가속기에서 Convolution 뒤의 출력 처리와 Fully Connected 연산기를 맡았고, 송신 보드의 ArUco 글자 영역 추출(C)과 송수신 Web UI를 만들었습니다.

| 파트 | 한 일 |
|:--|:--|
| CNN 모델 | LeNet-5 계열 후보 비교, 3×3 구조 확정, 대문자 26클래스 재학습, RTL 검증용 layer 출력 추출 |
| Output Buffer, ReLU & Quantization | Conv 부분합 누적, 40-bit → 16-bit 양자화, Max Pooling용 채널 순서 재정렬 RTL |
| Fully Connected | 400 → 120 → 84 → 26 FC RTL, 층별 전용 엔진(DSP 40)과 공유 엔진(DSP 20) 설계·비교 |
| ArUco 크롭 | 마커 검출부터 렌즈 왜곡 보정, 원근 보정, 112×112 글자 칸 5개 추출까지 PS C 구현 |
| Web UI | 송신부 전처리 단계·CNN 인식 결과 화면, 수신부 문자 표시 |

전체 시스템과 다른 파트 설명은 [LightLetter README](https://github.com/mumallaeng/LightLetter)에 있습니다.

## 설계

### CNN 모델 구조

28×28 입력에서 하드웨어로 옮기기 쉬운 구조를 찾기 위해 padding, FC1 크기, Conv 층 수, LeNet-5 변형(3×3, 원형, 현대식)을 Python에서 비교했다. 정확도와 BRAM 사용량을 함께 보고 3×3 Convolution 두 번 + 2×2 Max Pooling 두 번 + FC 400 → 120 → 84 → 26 구조로 확정했다. 처음에는 영문자와 숫자 36클래스로 시작했다가 대문자 26클래스로 다시 학습했고, 각 층 출력을 JSON으로 뽑아 C 골든 모델과 RTL testbench의 기준값으로 썼다.

<ImgTag filename="lightletter-conv-zero-gating.png" alt="Convolution Layer와 Zero Gating Array" />

그림 2. 하드웨어로 옮긴 Convolution Layer. Line Buffer와 MAC Array 사이의 Zero Gating Array가 입력 0일 때 곱셈을 막는다.

### Output Buffer, ReLU & Quantization

- MAC Array가 3채널씩 계산한 부분합을 받아, Phase로 나눠 계산한 부분합을 bias와 이전 저장값에 더해 출력 채널별로 누적한다.
- 누적이 끝난 40-bit 값은 ReLU로 음수를 없애고 Quantizer에서 16-bit로 줄인다.
- 픽셀 순서로 도착한 채널 값을 3채널 그룹으로 묶어 저장하고, Max Pooling이 한 채널의 픽셀을 연속으로 받도록 채널 순서로 다시 읽는다. 읽기 경로는 BRAM으로 합성되도록 모델링했다.
- 누적, ReLU, 양자화를 레지스터 단계로 나누고 데이터와 valid를 같은 클록에 등록해 MAC Array 출력과 Max Pooling 입력을 맞췄다.

### Fully Connected

Flatten한 400개 입력을 120 → 84 → 26으로 줄이고, 마지막 출력에서 ArgMax로 글자를 고른다. 두 구조를 만들어 비교했다.

- **층별 전용 엔진(DSP 40):** FC1·FC2·FC3에 MAC을 25·10·5개씩 둔다. 입력이 들어오는 동안 층별로 계산을 겹칠 수 있다.
- **공유 엔진(DSP 20):** 층별 입력을 Feature Buffer(LUT 기반 distributed RAM)에 두고, FC Controller가 Layer MUX와 Weight·Bias 주소를 바꿔 세 층이 MAC 20개를 차례로 쓴다.

층마다 양자화 시프트(`SCALE_EXP` 16/15/14)를 따로 두어 Python 모델과 같은 정수 결과를 내도록 맞췄다.

공유 엔진으로 줄이는 과정에서 MAC 타이밍도 다시 잡았다. 처음 짠 MAC은 곱셈 뒤 덧셈 트리가 한 클록에 몰려 조합 경로가 길었다. 덧셈 트리를 균형 있게 다시 묶고 중간에 파이프라인 레지스터를 넣었으며, 피연산자와 곱셈 결과는 DSP48E1 내부 레지스터에 등록했다. 최종 공유 엔진은 100 MHz에서 setup 여유 +1.051 ns였다. 파이프라인이 5단으로 늘어난 만큼 C 골든 모델도 같은 구조로 고쳐 bit-exact 비교를 유지했다.

### ArUco 크롭

화이트보드 둘레의 ArUco 마커 6개로 글자 칸 5개의 위치를 잡는다. 1280×720 프레임에서 마커를 검출하고, 카메라 캘리브레이션 값으로 렌즈 왜곡을 보정한 뒤 homography로 화이트보드를 정면 좌표로 옮긴다. 칸마다 bilinear 보간으로 112×112 RGB 이미지를 만들어 DMA로 PL 전처리에 넘긴다. OpenCV 기준 구현을 Python notebook으로 먼저 만들고, 같은 단계를 Vitis에서 쓸 수 있게 C로 옮겼다. 마커가 일부 가려져도 남은 마커로 homography를 채우고, 맞춤 오차(RMS)를 함께 돌려준다.

## 구현

- **C 골든 모델:** Output Buffer, ReLU & Quantization, Fully Connected를 RTL과 같은 순서·비트 폭으로 C에 먼저 구현하고, Python에서 뽑은 벡터로 테스트했다. FC는 RTL의 5단 MAC 파이프라인까지 C에 그대로 옮겼다.
- **RTL:** Verilog로 구현하고 Vivado out-of-context 합성으로 모듈 단위 타이밍과 자원을 확인했다.
- **ArUco C:** `aruco_crop_run()` 하나로 프레임 → 칸 5개를 처리하고, 칸별 성공 여부와 마커 좌표를 결과 구조체로 돌려준다.
- **송신 Web UI:** Zybo HDMI 출력을 USB 캡처보드로 받아, 보드와 같은 ArUco 크롭 → 전처리 단계를 PC에서 재현해 보여 준다. 보고 싶은 전처리 단계를 골라 띄우고, 칸별 인식 글자와 상위 3개 logit, 28×28 CNN 입력값을 확인하고 저장할 수 있다.
- **수신 Web UI:** 최근 수신 문자와 누적 문자열을 나눠 표시하도록 고쳤다.

## 검증·결과

### 골든 모델 비교

같은 입력을 Python QAT 모델, C 골든 모델, RTL에 넣어 세 출력이 같은지 확인했다. FC는 5개 입력 조건에서 logit 26개가 RTL, 배선 후 netlist, timing simulation 모두 bit-exact였다.

<ImgTag filename="lightletter-report-28.png" alt="CNN 동작 검증" />

그림 8. CNN 동작 검증

### FC 두 구조 비교

같은 조건에서 FC만 다르게 한 두 빌드를 비교했다. FC 단독은 out-of-context 합성·배선 결과이고, 보드 값은 Zybo Z7-20에서 70장 testset을 두 빌드 번갈아 5회씩 잰 평균이다.

| 항목 | 공유 엔진(DSP 20) | 전용 엔진(DSP 40) |
|:--|:--|:--|
| DSP48E1 | 20 | 40 |
| LUT / FF | 1,832 / 2,225 | 2,632 / 2,239 |
| Setup WNS (10 ns) | +1.051 ns | +0.919 ns |
| 보드 전처리+CNN 시간 | 271.44 µs | 257.37 µs (−5.2%) |
| 보드 대기 전력 | 2,680.6 mW | 2,778.7 mW (+98.1 mW) |
| inference당 보드 에너지 | 1,096.0 µJ | 1,093.9 µJ |
| PL 인식 정답 (70장) | 65 | 65 |

공유 엔진은 DSP를 절반만 쓰고 대기 전력이 낮았고, 전용 엔진은 입력이 띄엄띄엄 들어오는 보드 조건에서 14 µs 빨랐다. inference 한 번의 에너지는 사실상 같았다.

### 팀 결과

CNN 가속기 전체는 CPU(667 MHz) 대비 연산 시간 6.22배(2582.13 µs → 415.15 µs), 전력 57.7%, 에너지 93.2%를 줄였다. 최종 시연에서는 'HELLO' 다섯 글자를 촬영·인식해 레이저로 보내고 수신부에서 같은 문자열을 복원했다.

## 문제 해결

### 대기 중에도 나가는 전력

FC 단독 전력을 SAIF로 보면 입력이 없는 대기 상태에서 전용 엔진이 74 mW, 공유 엔진이 5 mW였다. 차이는 가중치 ROM이었다. 처음 구조는 ROM을 매 클록 읽었고, 공유 엔진은 MAC을 발행하는 클록에만 읽도록 read enable을 넣었다. 보드에서 잰 대기 전력 차이 98 mW도 이 값에 레귤레이터 손실을 더한 크기와 맞았다.

## 배운 점

- 실제 화이트보드 촬영 입력은 학습 데이터와 기울기, 배경, 글자 크기가 전부 달랐다. 모델보다 앞단의 크롭과 전처리가 인식률을 더 크게 좌우하는 걸 보면서 전처리가 정말 중요하다는 걸 느꼈다.
- RTL을 바로 짜기보다 C 골든 모델을 같은 비트 폭과 순서로 먼저 만들어 둔 게 가장 도움이 됐다. 파이프라인을 몇 번을 바꿔도 bit-exact 비교 한 번으로 맞는지 바로 확인할 수 있어서, 고치는 게 두렵지 않았다.
- DSP를 절반으로 줄인 공유 엔진이 당연히 느릴 거라고 생각했는데, 보드에서 재 보니 차이는 14 µs였고 에너지는 거의 같았다. 구조를 고를 때는 짐작보다 실제 입력 조건에서 잰 숫자를 믿어야 한다는 걸 배웠다.
