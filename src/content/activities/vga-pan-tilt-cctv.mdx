## 담당 역할

- **설계 대상:** 서보 제어부 `servo_top` (`ctrl_mode_mux`, `axis_ctrl` 통합, `servo_pwm` 2채널)과 보드 시험용 `servo_pwm_check_sw`
- **목적:** 영상 추적 오차와 조이스틱 변화량을 하나의 각도 제어 경로로 받아, SG90 두 개를 브래킷 허용 범위 안에서 50 Hz PWM으로 구동
- **검증 방식:** 각도별 펄스 폭과 20 ms 주기를 확인하는 self-check testbench, 실제 조이스틱 RTL과 서보를 연결한 통합 testbench, 서보 입력 직전까지 영상 파이프라인의 Python 골든 모델 bit-exact 비교, Basys 3 실기 시연

| 파트 | 한 일 |
|:--|:--|
| `ctrl_mode_mux` | 자동 모드 `frame_dx/dy`와 수동 모드 `joy_dx/dy` 중 하나를 고르고 갱신 신호를 함께 넘김 |
| `servo_pwm` | 각도 → High count 변환, 20 ms 주기 PWM, 주기 경계에서만 목표값 반영 |

## 설계

### `servo_top` 구조

`servo_top`은 `ctrl_mode_mux` → `axis_ctrl` → `servo_pwm_pan`/`servo_pwm_tilt` 순서로 연결된다. 자동 모드와 수동 모드가 같은 `axis_ctrl`을 공유하도록 입력 선택을 맨 앞에 두었다. 자동 모드는 객체 검출이 유효할 때의 `frame_done`, 수동 모드는 `joy_done`을 갱신 신호로 쓰고, 선택한 변화량과 갱신 신호를 함께 넘겨 두 모드의 갱신 주기가 섞이지 않게 했다.

<ImgTag filename="vga-readme-10.png" alt="servo_top 구조" />

그림 2. `servo_top` 구조

### 각도 누적과 범위 제한

`axis_ctrl`은 입력 변화량에 5/16°/count 이득을 적용하고, 한 번에 반영하는 변화량을 최대 ±20°로 제한한 뒤 현재 각도에 누적한다. 결과는 브래킷 구조에 맞춰 Pan 15°\~165°, Tilt 25°\~155° 안으로 자른다. 각도 이동은 `move_tick`에 맞춰 한 단계씩 진행한다.

<ImgTag filename="vga-readme-13.png" alt="각도 누적과 범위 제한" />

그림 3. 변화량 → 각도 변환 → 각도 갱신 → 범위 제한

### PWM 생성

`servo_pwm`은 각도 명령을 High count로 바꾸고 20 ms 주기 카운터와 비교해 PWM을 만든다. 100 MHz에서 20 ms는 2,000,000 count이고, High 구간은 1 ms(0°) + 각도 × count/degree로 1\~2 ms 사이에서 정한다. 목표 High count는 PWM 주기 경계에서만 반영해, 출력 중인 펄스의 폭이 중간에 바뀌지 않게 했다.

| 기준 각도 | 명목 High 시간 | 100 MHz 기준 count |
|:--|:--|:--|
| 0° | 1.0 ms | 100,000 |
| 90° | 1.5 ms | 150,000 |
| 180° | 2.0 ms | 200,000 |

그림 4. 각도 → 펄스 폭 → 20 ms 주기 → Pan/Tilt 출력

## 구현

- **RTL:** `ctrl_mode_mux`, `servo_pwm`, `servo_top`을 SystemVerilog로 작성했다. 각 축의 PWM은 같은 `servo_pwm`을 두 번 인스턴스해 만든다.
- **보드 시험 모드:** 통합 전에 서보만 따로 확인하려고 스위치로 각도를 직접 주는 `servo_pwm_check_sw`를 만들고, 이어서 조이스틱 출력을 서보에 바로 연결해 Basys 3에서 움직임을 확인했다.
- **각도 이동 주기 분리:** 새 목표가 들어온 클록에 각도가 바로 한 단계 움직이던 것을 `move_tick`에서만 움직이도록 바꿔, 갱신 신호가 몰려도 이동 속도가 일정하게 했다. 같은 수정에서 조이스틱 polling 주기도 올렸다.
- **좌표 → 각도 경로 정렬:** `coord_to_angle` 파이프라인이 valid 신호와 어긋나던 부분을 김동현과 함께 맞췄다.

### 영상 파이프라인 골든 모델

서보 입력 직전까지 영상 경로가 맞는지 확인하려고, 카메라 프레임 버퍼 이후 녹색 검출 → 3×3 노이즈 필터 → Bounding Box → 화면 출력을 표준 라이브러리 Python으로 사이클 단위까지 옮긴 골든 모델(`gmodel.py`)을 만들었다. 같은 입력 이미지를 RTL 통합 하네스(`tb_top_video_golden.sv`)에도 넣고, 6개 단계 산출물(프레임 버퍼, 녹색 마스크, 정리된 마스크, bbox, 서보 입력 `frame_dx/dy/valid`, 최종 화면)을 SHA-256으로 대조했다. iverilog와 Vivado 2020.2 xsim 모두 320×240과 640×480 두 설정에서 6/6 MATCH였다.

## 문제 해결

### 2배 스트림에서 벌어지는 Bounding Box

- **증상:** 골든 모델 하네스로 FULLSCREEN(640×480) 출력을 비교하자, 공만 감싸야 할 박스가 바닥 반점까지 넓게 벌어졌다(bbox 44\~301, 68\~221).
- **원인:** FULLSCREEN에서는 같은 소스 픽셀이 가로로 두 번, 세로로 두 줄에 걸쳐 검출 파이프라인에 들어간다. 그래서 단일 녹색 잡음 픽셀도 3×3 다수결을 통과했다.
- **수정:** 소스 픽셀당 첫 번째 복제본만 검출 경로에 넣는 게이트를 만들어, Top에 넣었다 뺄 수 있는 패치(`patch_top.py`)로 확인했다. 게이트를 넣은 640×480 결과의 마스크와 bbox(173\~227, 69\~123)가 1:1인 320×240 결과와 해시까지 같아졌다. 화면 출력은 그대로 640×480이다.

## 배운 점

- 서보 PWM은 시뮬레이션에서 펄스 폭이 맞아도, 실제 브래킷에 달면 끝단 간섭 때문에 쓸 수 있는 각도가 달랐다. 명령각과 실제 기계 각도를 따로 봐야 한다는 걸 배웠다.
- 육안으로는 '박스가 가끔 튄다' 정도로만 보이던 문제가, 골든 모델과 단계별 해시를 비교하자 어느 단계에서 왜 생기는지 바로 드러났다. 비교 기준을 먼저 만들어 두는 게 디버깅 시간을 가장 많이 줄여 줬다.
- 서보 경로를 맡았지만 서보 입력 앞단의 영상 경로까지 검증하면서 내 모듈이 받는 값이 맞는지부터 확인하는 습관이 생겼다.
